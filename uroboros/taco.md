# TACO 설계 문서 (의도/목적/문서 체계/운영 원칙)

## 1) 문서 목적

이 문서는 `taco`의 구현 세부(코드 구조, 함수, 클래스, 런타임 트릭)를 설명하지 않는다.  
대신 아래 네 가지를 설계 관점에서 고정한다.

- 무엇을 해결하려는 도구인가 (의도와 목적)
- 어떤 문서를 기준으로 움직이는가 (문서 종류와 책임)
- 작업이 어떤 순서로 흘러가는가 (운영 흐름)
- 어떤 원칙으로 일관성을 유지하는가 (거버넌스, 품질, 변경 규칙)

핵심은 하나다:  
`taco`는 “작업 단위 실행에 필요한 컨텍스트를 문서에서 결정론적으로 조립”하기 위한 도구다.

## 2) 제품 의도와 목표

## 2.1 제품 의도

- 계획(Plan)과 실행(Build) 사이를 문서 기반으로 연결한다.
- 사람이 바뀌어도 같은 입력이면 같은 맥락 묶음(pack)이 나오게 한다.
- 작업 단위 기록을 남겨, 왜 그렇게 실행했는지 추적 가능하게 만든다.

## 2.2 1차 목표

- Task 단위 컨텍스트 팩 생성 (`task.pack`, `plan.pack`, `plan.intent.index`)
- 작업 기록/완료/차단 흐름 표준화 (`task.record`, `task.complete`, `task.block`)
- 문서 일부를 참조 단위로 읽고 갱신하는 경로 제공 (`doc.snippet`, `doc.section.*`)
- 운영 원칙을 문서화한 거버넌스 레이어 제공 (`convention.get`, 거버넌스 문서)

## 2.3 비목표

- 프로젝트 코드 자체를 자동으로 구현해주는 범용 코딩 에이전트가 되는 것
- 문서 전체를 무작위로 탐색하는 검색 엔진이 되는 것
- 팀별 정책을 코드 하드코딩으로 강제하는 것

## 3) 설계 원칙

- 결정론: 같은 입력/같은 문서 상태면 동일한 결과를 반환한다.
- 추적성: 선택 근거(참조 문서, 경로, 이유 코드)가 결과에 남아야 한다.
- 얇은 계약: 도구 이름과 I/O 계약은 단순하고 안정적으로 유지한다.
- 문서 SSOT: 핵심 지식은 `.context/` 문서에 있고, 툴은 이를 조립/검증한다.
- 분리: 계획 의도, 아키텍처 설계, 실행 태스크, 거버넌스 규칙의 책임을 섞지 않는다.
- 최소 적재: 필요한 문맥만 로딩한다. 전체 문서 스캔은 예외 상황으로 제한한다.

## 3.1 `src/taco` 아키텍처 의도 (헥사고널 패턴)

- `src/taco`는 헥사고널(Ports and Adapters) 구조를 기본 원칙으로 사용한다.
- 코어 도메인(`core/*`)은 입출력 구현 세부를 모르고, 오직 규칙/유스케이스를 담당한다.
- 포트(`ports/*`)는 도메인이 요구하는 저장소/리포지토리/외부 상호작용 계약을 정의한다.
- 어댑터(`adapters/*`)는 파일시스템, git, mcp transport 같은 구체 구현을 제공한다.
- 애플리케이션 경계(`apps/*`)는 CLI/MCP 진입점을 제공하되, 코어 규칙을 우회하지 않는다.
- 이 구조의 목적은 세 가지다:
  - 테스트 가능성: 코어 유스케이스를 I/O 없이 검증 가능하게 유지
  - 교체 가능성: Python 구현에서 Rust 런타임으로 교체해도 계약 유지
  - 운영 안정성: 인터페이스(도구 계약)와 내부 구현 변화의 결합도 최소화

## 4) 문서 체계와 책임

## 4.1 루트 체계

- `.context/project/`: 프로젝트 목적/계획/아키텍처/태스크
- `.context/governance/`: 코드/문서/깃 규칙
- `taco.yaml`: 경로/우선순위/필수 ref/예산 정책

## 4.2 문서 종류

- Overview
  - 프로젝트 목적, 범위, 비목표를 요약한다.
- Intent 문서 (`I-*.md`)
  - “왜 바꾸는가”를 정의한다.
  - 실행 태스크로 쪼개지기 전의 기획 단위다.
- Plan 문서 (`plan.md`)
  - 어떤 순서로 실행할지, 활성/차단/다음 작업 상태를 관리한다.
- Architecture 문서 (`architecture/*`)
  - 모듈/흐름/스키마 관점의 구조 결정을 담는다.
- Task 문서 (`tasks/T-*.md`)
  - 실행 단위. 목표/범위/접근/검증/결과를 명시한다.
- Governance 문서 (`governance/*`)
  - 코드/문서/깃 운영에서 반드시 지킬 규칙을 담는다.

## 4.3 문서 간 연결 규칙

- 문서 연결은 가능한 `id` 기반 참조를 우선한다.
- Task는 Intent/Architecture/Plan을 참조하되, 정의를 복붙하지 않는다.
- Plan은 작업 상태를 관리하고 설계 원문 저장소가 되지 않는다.
- Architecture는 전역 구조를 보존하고 Task별 임시 판단을 흡수하지 않는다.

## 5) 운영 흐름 (Plan -> Build -> Record)

## 5.1 Plan 흐름

1. Intent를 선택한다.
2. Intent 중심 인덱싱/팩을 구성한다.
3. 필요 시 아키텍처/플랜 문서를 업데이트한다.
4. 실행 가능한 Task 단위로 분해한다.

## 5.2 Build 흐름

1. Task를 선택한다.
2. Task 팩을 구성한다.
3. 구현 전/후 체크를 수행한다.
4. 결과를 task 문서에 기록하고 완료/차단 상태를 반영한다.

## 5.3 Record 흐름

- 작업 중 판단 근거는 `Implementation Approach`/`Verification Approach`에 유지한다.
- 실제 결과는 `Implementation Result`/`Verification Result`에 남긴다.
- 차단 시 이유 코드를 남겨 재현 가능한 상태 전이를 보장한다.

## 6) 문서 품질 규칙

- 모든 핵심 문서는 front matter를 가진다.
- `id`는 안정 식별자이며, 변경 시 하위 참조를 함께 갱신한다.
- 태스크 문서는 실행 가능한 수준의 목표/범위/검증 절차를 가진다.
- 거버넌스 문서는 “권고”가 아니라 운영 기준선으로 사용한다.
- 문서 변경은 가능한 단일 책임 단위로 쪼개 기록한다.

## 7) 거버넌스의 역할

거버넌스는 세 가지를 보장한다.

- 코드 원칙: 일관된 설계/검증/에러 모델
- 문서 원칙: SSOT 유지, 문서 책임 분리, 참조 무결성
- git 원칙: 브랜치/커밋/PR/병합 안전 기준

즉, 거버넌스는 구현팀 성향이 아니라 시스템 계약의 일부다.

## 8) `taco init` 설계 기준

`taco init`은 새로운 저장소가 아래 상태를 즉시 갖추게 해야 한다.

- 실행 가능한 기본 문서 골격
- 규칙이 명시된 거버넌스 문서
- 도구 실행을 위한 기본 `taco.yaml`

특히 `.context/governance/*`는 임시 요약본이 아니라  
“기준 템플릿 원문 그대로” 생성되어야 한다.

## 9) 배포 일관성 요구사항

- 로컬 개발 환경과 배포된 패키지에서 `init` 결과가 같아야 한다.
- 템플릿 리소스는 패키지에 포함되어야 한다.
- 거버넌스 템플릿은 단일 원본(canonical source)을 사용해야 한다.
- 회귀 테스트는 생성 결과가 템플릿 원문과 일치함을 검증해야 한다.

## 10) 변경 관리 원칙

- 도구 계약(도구명, 입력/출력)은 가능한 하위 호환을 유지한다.
- 문서 체계 변경은 Plan/Architecture/Governance 모두에서 합의된 후 반영한다.
- 거버넌스 변경은 `init` 결과에도 반영되어야 하며, 배포 포함 여부를 함께 검증한다.
- “새 기능 추가”보다 “현재 흐름의 안정성”을 우선한다.

## 11) 완료 기준 (Definition of Done)

이 설계가 충족되려면 아래가 만족되어야 한다.

- `taco` 사용자 관점에서 Plan/Build 흐름이 끊기지 않는다.
- Task/Intent/Plan/Architecture/Governance의 책임 경계가 유지된다.
- `taco init` 후 즉시 최소 운영 가능한 문서 세트가 생성된다.
- 생성된 거버넌스 문서가 템플릿 원문과 동일하다.
- 로컬 실행과 배포 실행의 초기화 결과가 동일하다.
